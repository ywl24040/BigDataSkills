# 维度建模核心思想

> 维度建模（Dimensional Modeling）是 Ralph Kimball 提出的一套数据仓库建模方法论，以查询性能、易理解性和可扩展性为核心目标，广泛应用于数据分析与商业智能（BI）场景。

---

## 一、核心概念

### 1.1 事实表（Fact Table）

事实表是维度建模的核心，存储业务过程的**度量值（Measure）**。每一行代表一个业务事件或状态快照。

| 特性 | 说明 |
|------|------|
| 粒度 | 事实表中一行数据所代表的业务含义（最细粒度） |
| 度量 | 可累加的数值型指标，如金额、数量、次数 |
| 外键 | 关联到各维度表的代理键 |
| 稀疏性 | 并非所有事实行都关联所有维度 |

**事实表的三种类型：**

| 类型 | 描述 | 示例 |
|------|------|------|
| **事务事实表** | 记录每个业务事件，一行一事 | 订单明细、交易流水 |
| **周期快照事实表** | 按固定周期记录状态快照 | 每日库存、月度余额 |
| **累积快照事实表** | 跟踪业务流程中多个里程碑 | 订单生命周期（下单→支付→发货→签收） |

### 1.2 维度表（Dimension Table）

维度表描述业务实体，提供**分析视角（Who, What, Where, When, Why）**。

| 特性 | 说明 |
|------|------|
| 主键 | 代理键（Surrogate Key），避免业务键变更 |
| 属性 | 描述性字段，作为查询的筛选条件和分组依据 |
| 层级 | 维度属性间的父子关系，如 国家→省→市→区 |
| 宽表 | 维度表通常较宽，包含大量描述性属性 |

- 维度表，也是为了先出多成嵌套查询，提升查询效率
- 维度表，管理事实表即可，或者上一层的维度表

## 二、模型架构

### 2.1 星型模型（Star Schema）

```
                    ┌─────────────┐
                    │   dim_date   │
                    └──────┬──────┘
                           │
        ┌─────────────┐    │    ┌─────────────┐
        │ dim_product │────┼────│ dim_customer │
        └─────────────┘    │    └─────────────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
        ┌─────┴─────┐   中心事实表   ┌──┴──────────┐
        │ dim_store │  fact_sales   │ dim_payment  │
        └───────────┘               └─────────────┘
```

- 维度表**直接**连接事实表，不经过中间表
- 维度表存在冗余，但查询性能最优
- **推荐作为默认建模方案**

### 2.2 雪花模型（Snowflake Schema）

```
    dim_date ──→ fact_sales ←── dim_product ←── dim_category ←── dim_brand
                    │
                    ├── dim_customer ←── dim_city ←── dim_province
                    │
                    └── dim_store ←── dim_region
```

- 维度表被进一步规范化，拆分出子维度
- 减少冗余存储，但查询时需更多 JOIN
- **一般不推荐**，除非维度层级极其复杂且存储压力大

### 2.3 星座模型（Galaxy Schema / Fact Constellation）

- 多个事实表**共享**维度表
- 是数据仓库中常见的实际形态
- 依赖于**一致性维度**和**总线矩阵**来实现

## 三、维度建模关键技术

### 3.1 缓慢变化维度（SCD - Slowly Changing Dimension）

维度属性会随时间变化，处理策略如下：

| 类型 | 策略 | 说明 | 适用场景 |
|------|------|------|----------|
| **SCD Type 0** | 保留原值 | 属性不可变 | 出生日期、身份证号 |
| **SCD Type 1** | 覆盖更新 | 直接更新旧值，不保留历史 | 用户昵称修正 |
| **SCD Type 2** | 拉链表 | 新增行 + 生效/失效时间 + 当前标识 | 用户地址变更（需保留历史） |
| **SCD Type 3** | 新增列 | 保留上一个值在单独列中 | 仅需追溯最近一次变更 |
| **SCD Type 4** | 历史表 | 当前值和历史值分表存储 | 主表性能要求高 |
| **SCD Type 6** | 混合型 | 1+2+3 组合，同时覆盖更新、新增行、历史列 | 复杂业务需求 |

### 3.2 退化维度（Degenerate Dimension）

当一个维度仅剩一个**标识符**（如订单号、运单号）而无其他属性时，将其直接存储在事实表中，不单独建维度表。

```
fact_orders: order_id(退化维度), product_key, customer_key, date_key, amount
```

> CS_CreditMeansuremnTRACE, CS_

### 3.3 杂项维度（Junk Dimension）

将多个**低基数、独立、标志位**类型的属性合并到一个维度表中：

```
dim_junk: junk_key, is_new_customer, payment_method, promotion_flag, ...
```

### 3.4 维度层次（Hierarchy）

维度属性间存在自然层级关系：

```
年 → 季 → 月 → 周 → 日          （时间层次）
国家 → 省 → 市 → 区/县           （地理层次）
品类 → 大类 → 中类 → 小类 → SKU   （产品层次）
```

在星型模型中，层次被**扁平化**存储在同一个维度表中。

## 四、总线矩阵（Bus Matrix）

总线矩阵是 Kimball 方法论的核心工具，用于规划企业数据仓库的整体架构。

### 4.1 矩阵结构

| 业务过程 \ 维度 | 日期 | 客户 | 产品 | 门店 | 渠道 | 员工 |
|----------------|------|------|------|------|------|------|
| 销售订单 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| 库存快照 | ✓ | | ✓ | ✓ | | |
| 采购入库 | ✓ | | ✓ | ✓ | | ✓ |
| 客户投诉 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

- **行**：业务过程（对应事实表）
- **列**：一致性维度（对应维度表）
- **交叉点**：标记该业务过程是否使用该维度

### 4.2 一致性维度（Conformed Dimension）

同一个维度在多张事实表中有相同的**含义**和**内容**，确保跨业务过程分析的一致性。

### 4.3 总线矩阵的实施步骤

1. **识别业务过程**：从企业价值链出发，列出所有核心业务过程
2. **声明粒度**：明确每个事实表的粒度
3. **识别维度**：为每个事实表确定关联的维度
4. **识别事实**：确定每个事实表的度量指标

## 五、维度建模设计步骤

### 5.1 四步设计法

```
第一步：选择业务过程
   ↓
第二步：声明粒度
   ↓
第三步：识别维度
   ↓
第四步：识别事实
```

### 5.2 详细说明

**第一步：选择业务过程**

- 从业务需求出发，确定要建模的业务过程
- 业务过程 = 动词 + 名词，如"创建订单"、"支付订单"、"发货"

**第二步：声明粒度**

- 确定事实表中一行代表什么
- 粒度决定了分析的精细程度
- **原则：尽量选择最细粒度**（原子粒度）

**第三步：识别维度**

- 回答"5W1H"：Who, What, Where, When, Why, How
- 每个维度提供一种分析视角

**第四步：识别事实**

- 确定可度量的指标
- 必须与粒度保持一致
- 区分可加事实、半可加事实、不可加事实

## 六、设计原则总结

| 原则 | 说明 |
|------|------|
| **原子粒度优先** | 事实表保持最细粒度，满足多维度下钻需求 |
| **扁平化维度** | 采用星型模型，避免过度规范化 |
| **代理键** | 维度表使用无业务含义的代理键作为主键 |
| **一致性维度** | 跨业务过程共享统一的维度定义 |
| **业务驱动** | 模型设计以业务需求为导向，而非技术驱动 |
| **降低耦合** | 每个事实表只对应一个业务过程 |
| **可扩展性** | 预留扩展空间，新增维度或度量不影响现有结构 |

## 七、维度建模 vs 范式建模

| 对比维度 | 维度建模（Kimball） | 范式建模（Inmon） |
|----------|---------------------|-------------------|
| 核心理念 | 自下而上，从数据集市到数据仓库 | 自上而下，先建企业级数据仓库 |
| 表结构 | 星型/雪花模型 | 3NF 规范化 |
| 查询性能 | 高（减少 JOIN） | 较低（多表 JOIN） |
| 存储冗余 | 有冗余 | 低冗余 |
| 易理解性 | 业务人员友好 | 技术人员友好 |
| 适用场景 | BI 分析、报表 | 企业级数据仓库、ODS 层 |

## 八、常见问题与应对

| 问题 | 应对策略 |
|------|----------|
| 维度属性过多 | 拆分维度表，或使用杂项维度 |
| 事实表膨胀过快 | 聚合事实表，定期归档历史数据 |
| 多对多关系 | 桥接表（Bridge Table） |
| 实时性要求 | Lambda/Kappa 架构，实时层 + 离线层互补 |
| 数据质量 | 维度表 ETL 优先加载，确保维度数据准确性 |
