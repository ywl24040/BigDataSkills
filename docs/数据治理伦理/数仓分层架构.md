# 数据仓库分层架构

> 数据分层是数据仓库建设的核心方法论，通过将数据按加工深度和用途分层，实现数据的高效管理、复用和质量保障。

---

## 一、为什么需要分层

| 目标 | 说明 |
|------|------|
| **清晰的数据结构** | 每一层有明确的职责和作用域，便于理解和维护 |
| **数据血缘追踪** | 通过分层可以清晰追溯数据从源头到应用的完整链路 |
| **减少重复开发** | 中间层数据可被多个上层应用复用 |
| **简化问题定位** | 数据异常时可快速定位到具体层级 |
| **统一数据口径** | 公共层沉淀统一指标，避免口径不一致 |
| **屏蔽底层变更** | 源系统变更时，只需调整 ODS 层，上层无感知 |

---

## 二、经典分层架构

### 2.1 分层总览

```
┌─────────────────────────────────────────────────────────┐
│                    应用层 (ADS / APP)                     │
│            面向具体应用场景，个性化报表与数据产品            │
├─────────────────────────────────────────────────────────┤
│                  公共汇总层 (DWS / SUM)                    │
│              轻度汇总的公共指标，面向主题域                  │
├─────────────────────────────────────────────────────────┤
│                    明细宽表层 (DWD)                        │
│            业务过程明细数据，维度建模，宽表设计               │
├─────────────────────────────────────────────────────────┤
│                    维度层 (DIM)                           │
│                  公共维度表，一致性维度                      │
├─────────────────────────────────────────────────────────┤
│                   操作数据层 (ODS)                         │
│              原始数据，贴源层，保持源系统结构                 │
├─────────────────────────────────────────────────────────┤
│                   临时数据层 (TMP)                         │
│                临时计算、中间结果、过渡数据                   │
└─────────────────────────────────────────────────────────┘
```

### 2.2 各层详细说明

#### ODS 层（Operational Data Store）—— 操作数据层 / 贴源层

| 特性 | 说明 |
|------|------|
| 数据来源 | 业务系统数据库、日志、API、文件等 |
| 数据特点 | 与源系统结构一致，不做或极少做清洗转换 |
| 同步策略 | 全量同步 / 增量同步 / 断点续传 |
| 存储周期 | 通常保留 7-30 天 |
| 压缩方式 | 高压缩比存储，降低存储成本 |

**核心原则：**

- 保持源数据的原始性，不进行业务逻辑处理
- 增加分区字段（如 `dt` 日期分区），便于按天管理
- 记录数据接入时间戳，用于数据血缘追踪
- 对敏感字段进行脱敏处理

**同步策略对比：**

| 策略 | 适用场景 | 优点 | 缺点 |
|------|----------|------|------|
| 全量同步 | 小表、维度表 | 简单可靠 | 大数据量耗时长 |
| 增量同步 | 大表事务数据 | 效率高 | 需处理变更和删除 |
| CDC 同步 | 实时性要求高 | 低延迟 | 技术复杂度高 |
| 日志解析 | 数据库日志 | 无侵入 | 依赖数据库类型 |

---

#### DWD 层（Data Warehouse Detail）—— 明细数据层 / 数据明细层

| 特性 | 说明 |
|------|------|
| 数据来源 | ODS 层 |
| 建模方法 | 维度建模（星型模型） |
| 数据特点 | 清洗后、标准化、业务过程级别明细 |
| 粒度 | 与业务过程原子粒度一致 |

**核心处理步骤：**

1. **数据清洗**
   - 空值处理：填充默认值、删除或标记
   - 格式统一：日期格式、编码格式、大小写统一
   - 数据去重：按业务主键去重
   - 异常值处理：超出合理范围的值进行标记或剔除

2. **数据转换**
   - 字段映射：源字段 → 标准字段命名
   - 类型转换：字符串→数值、时间戳→日期
   - 编码解析：字典值转义、ID 关联名称
   - 维度退化：将高频使用的维度属性退化到事实表

3. **数据关联**
   - 维度关联：事实表关联维度表获取代理键
   - 多源整合：多个数据源的数据合并

4. **数据质量**
   - 完整性检查：必填字段非空
   - 一致性检查：关联键是否能在维度表中找到
   - 准确性检查：金额、数量等度量值合理性

**DWD 层典型事实表设计：**

```
fact_order_detail（订单明细事实表）
├── 业务键：order_id, order_item_id
├── 维度外键：date_key, customer_key, product_key, store_key
├── 度量值：quantity, unit_price, total_amount, discount_amount
├── 退化维度：order_no, coupon_code
└── 分区字段：dt
```

---

#### DIM 层（Dimension）—— 维度层

| 特性 | 说明 |
|------|------|
| 数据来源 | ODS 层维度表、DWD 层退化维度提取 |
| 核心要求 | 一致性维度，跨业务过程共享 |
| 更新策略 | SCD 缓慢变化维度处理 |

**维度表设计要点：**

- 使用代理键（Surrogate Key）作为主键
- 保留业务自然键，用于与源系统关联
- 处理缓慢变化维度（SCD Type 1/2/3）
- 维度属性扁平化，合并层级结构
- 添加时间戳字段（`create_time`, `update_time`, `start_date`, `end_date`）

**常见维度表：**

| 维度表 | 说明 | 典型属性 |
|--------|------|----------|
| dim_date | 日期维度 | 日期、年、季、月、周、星期、是否节假日 |
| dim_customer | 客户维度 | 客户ID、姓名、等级、注册日期、地区 |
| dim_product | 产品维度 | 产品ID、名称、品类、品牌、规格、单价 |
| dim_store | 门店维度 | 门店ID、名称、类型、地区、开业日期 |
| dim_channel | 渠道维度 | 渠道ID、渠道名称、渠道类型 |
| dim_payment | 支付维度 | 支付方式、支付平台、是否分期 |

---

#### DWS 层（Data Warehouse Service）—— 公共汇总层 / 服务层

| 特性 | 说明 |
|------|------|
| 数据来源 | DWD 层 + DIM 层 |
| 粒度 | 按主题、维度组合进行轻度汇总 |
| 核心目标 | 沉淀公共指标，统一数据口径 |

**汇总粒度示例：**

```
DWD 原子粒度：每笔订单明细
DWS 日汇总：  每日-每商品-每门店 的 销量/销售额/订单数
DWS 周汇总：  每周-每商品-每门店 的 销量/销售额/订单数
DWS 月汇总：  每月-每商品-每门店 的 销量/销售额/订单数
```

**DWS 层设计原则：**

- 面向主题域组织（交易、用户、商品、供应链等）
- 汇总最常用的维度组合，避免过度汇总
- 指标定义统一，消除口径歧义
- 可基于 DWS 直接生成报表，减少重复计算

---

#### ADS 层（Application Data Service）—— 应用数据层 / 应用层

| 特性 | 说明 |
|------|------|
| 数据来源 | DWS 层、DWD 层 |
| 数据特点 | 高度定制化，面向具体应用场景 |
| 输出形式 | BI 报表、数据大屏、数据 API、数据产品 |

**典型应用场景：**

- 经营日报/周报/月报
- 实时大屏监控
- 用户画像标签
- 推荐系统特征
- 风控模型输入
- 数据 API 服务

---

#### TMP 层（Temporary）—— 临时层

- 存放 ETL 过程中的中间结果
- 临时表、计算中间数据
- 数据生命周期短，可定期清理

## 三、数据流向

```
源系统（业务数据库、日志、文件）
        │
        ▼
    ┌───────┐
    │  ODS  │  ← 贴源层，原始数据
    └───┬───┘
        │
        ├──────────────┐
        ▼              ▼
    ┌───────┐      ┌───────┐
    │  DWD  │      │  DIM  │  ← 明细层 + 维度层
    └───┬───┘      └───┬───┘
        │              │
        └──────┬───────┘
               ▼
          ┌───────┐
          │  DWS  │  ← 汇总层
          └───┬───┘
              │
              ▼
          ┌───────┐
          │  ADS  │  ← 应用层
          └───────┘
```

**数据流向规则：**

- 上层可引用下层，下层不可引用上层
- 同层之间尽量避免依赖（特殊情况可引用 DIM 层）
- 跨层引用需谨慎，可能导致数据血缘混乱

## 五、命名规范建议

### 5.1 表命名规范

```
{层级前缀}_{主题域}_{业务含义}_{粒度后缀}_{分区标识}

示例：
ods_trade_order_detail_di        -- ODS层-交易域-订单明细-日增量(daily increment)
dwd_trade_order_detail_di        -- DWD层-交易域-订单明细
dim_date_df                      -- 维度表-日期维度-全量(daily full)
dws_trade_store_sales_1d         -- DWS层-交易域-门店销售-1日汇总
ads_trade_dashboard_daily        -- ADS层-交易域-经营日报
```

### 5.2 字段命名规范

- 统一小写 + 下划线分隔
- 代理键：`xxx_key`（如 `customer_key`, `date_key`）
- 业务键：`xxx_id`（如 `customer_id`, `order_id`）
- 度量值：描述性命名（如 `total_amount`, `order_count`）
- 时间戳：`xxx_time`（如 `create_time`, `update_time`）
- 标识位：`is_xxx`（如 `is_deleted`, `is_active`）
- 分区字段：`dt`（日期分区，格式 `yyyy-MM-dd`）

## 六、分层实施要点

| 要点 | 说明 |
|------|------|
| **ODS 保持原样** | 不对源数据做业务逻辑转换，只做最基础的格式化 |
| **DWD 做宽表** | 将关联维度属性退化到事实表，减少下游 JOIN |
| **DIM 做一致性** | 确保维度表在多个事实表间的一致性和可复用性 |
| **DWS 做公共指标** | 沉淀通用指标，统一口径，避免各处重复计算 |
| **ADS 做个性化** | 紧贴业务需求，快速响应，允许一定冗余 |
| **数据质量贯穿** | 每一层都需要数据质量监控，而非仅在最后校验 |
| **元数据管理** | 维护表级、字段级元数据，包括血缘、字典、口径说明 |

## 七、分层架构的演进

### 7.1 传统离线数仓

```
ODS → DWD → DWS → ADS
（T+1 批处理，延迟高，吞吐量大）
```

例子：

Callidus Incentive Management system

![image-20260822195237961](https://wren-images-1313141368.cos.ap-nanjing.myqcloud.com/imgs/image-20260822195237961.png)

### 7.2 Lambda 架构

```
实时链路：源系统 → Kafka → Flink → ADS（实时）
离线链路：源系统 → ODS → DWD → DWS → ADS（离线）
批流结合，实时层做近似计算，离线层做精准修正
```

### 7.3 Kappa 架构

```
全量链路：源系统 → Kafka → Flink → DWD → DWS → ADS
（全实时，无离线链路，通过消息队列重放实现历史计算）
```

### 7.4 湖仓一体（Lakehouse）

```
源系统 → 数据湖（Parquet/Iceberg/Hudi）→ 数据仓库 → 应用
统一存储层，兼容批流，支持 ACID 事务
```
